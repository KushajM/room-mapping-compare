How the room-mapping benchmark is built

How a pair of listings gets a label

One test case is one pair of supplier listings at one hotel. The question is always the same: do these two listings sell the same room that the hotel itself publishes?

1

Find the hotel's own website

Web search for the property's official site, checked against the hotel's name and city. Chain sites that block automated access are skipped, not worked around ( such hotels are listed for a licensed-content request).

2

Read its published room list

robots.txt is checked before any request; unreadable robots means skip. One request per two seconds per site, a self-identifying user agent, no IP rotation, no CAPTCHA solving, no headless browser.

3

Place supplier names by an exact rule

A supplier name is placed on a published room only if its normalised words equal that room's words exactly, it matches only one room, and no published room contains all its words plus more. Otherwise the rule abstains. No LLM, no prices, and no system's output is consulted.

4

Form pairs

SAME: both listings placed on the same published room. DIFFERENT: placed on two different rooms. A pair spanning a room and its own refinement (Deluxe Room vs Deluxe Room, Sea View) is excluded, not labelled. Labels stay on pairs; they are never closed into clusters.

Coverage: what the strict rule reaches

Strictness is the price of independence. Most listings are left unplaced, and that is reported rather than filled in.

Baselines, scored live on the dev hotels

Every submission is reported beside these. Wrong merges and missed matches are always shown as a pair and never combined: each one alone is won by a trivial answer.

Read the split columns with care. The strict rule only calls two listings the same room when both names carry exactly the published room's words. So a "different names" pair here differs only in word order, case or punctuation, never in a real facet. Grouping names by that same word set scores zero missed matches and near-zero wrong merges, and beats every system on this frame. The split rates on this page therefore measure easy splits only. The wrong-merge columns are the informative ones.

The sealed draw, and why the test half is not on this page
Frames: which listings a number is about
  • Panel frame (this page): every listing production actually sees at the hotel, uncapped. Pairs are sampled down to at most per hotel so large hotels don't dominate.
  • Release frame: at most 40 listings per hotel, small enough for someone outside Plexe to reproduce. 32 hotels / 1,609 pairs; built from the same rule.
  • Fair three-way frame (the comparison page): the 44 hotels where Vervotech and Plexe v2 both have saved outputs, restricted to names all three systems placed. Its numbers are not comparable with this page's, because the listings are different.

A number quoted without its frame is not a result. Every report names the frame first.

Abstention, on both sides
  • Gold side. A listing the rule cannot place is not guessed. Its reason is recorded (no exact match, could be a more specific room, matches several rooms, no room words after normalising), and its pairs are simply not in the gold.
  • Prediction side. A system may decline to place a listing below a level by marking it PARK:. By default parked pairs are removed from both rates and reported as a separate parked rate on every cell, along with what the rates would be if parking were charged, so parking cannot buy a quiet win.
  • Direction. A SAME pair can only expose a missed match; a DIFFERENT pair can only expose a wrong merge. A source that cannot see a direction contributes no denominator to it.

Known limitations
What came before v5, and why it was replaced
  1. Price-derived gold (v0–v1). Pairs were labelled from price behaviour inside the incumbent's own clusters. It could only ever see merges (a pair the system kept apart has no in-cluster price statistic), and 93.8% of its first DIFFERENT labels restated the deployed clusterer's own facets. Kept as a separate, merge-only diagnostic.
  2. LLM-assigned web gold (scraped_gold_v1). An LLM placed supplier names on scraped room lists, with verbatim-quote checks. Human review passed it only with an error band, and the snippet-based half failed. An LLM in the gold also cannot grade an LLM-based system fairly.
  3. v5 identity gold (this page). The LLM is removed from the gold entirely: placement is a deterministic exact-match rule, and the only other way in is blind human review. The cost is coverage, which is shown above.
